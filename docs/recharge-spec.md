# 充值与额度规范（2026-10-28）

## 1. 额度从哪来

用户的网关额度（μUSD）只有三个来源，流水里各自一种类型：

| 来源 | 流水类型（控制台显示） | 入口 |
|---|---|---|
| **管理员手动充值**（当前的核心能力） | `grant`「人工充值」 | 管理台「用量日志」→「手动充值与撤回」 |
| 兑换码 | `redeem`「兑换码」 | 运营在管理台生成，用户在控制台兑换 |
| 在线支付 | `recharge`「在线充值」 | 控制台「充值与流水」 |

另有消费 `consume`、平台撤回 `revoke`、邀请奖励 `invite`。

**没有「模拟充值」**：任何让用户不经付款给自己加额度的入口都不存在（2026-10-28 整体删除：
`POST /app/gateway/recharge/mock`、`NETONAPI_ENABLE_MOCK_RECHARGE`、控制台卡片）。测试 / 演练需要额度时一律用管理员手动充值。

## 2. 管理员手动充值

- 按**用户 ID 或用户名**查出账户（余额、在途预留、可用、流水），再「手动充值」或「撤回」。
- 金额**按美元填**，旁边实时显示换算后的 μUSD；提交 μUSD（`POST /admin/gateway/quota/grant` / `revoke`）。
- **凭据号**自动生成（`manual:YYYYMMDD-HHMMSS` / `revoke:…`），可改成工单号；同一凭据只入账一次（台账 ref 唯一），
  双击不会双发。
- 撤回是无条件扣减，允许把余额扣成负数（误发的额度被花掉后仍能收回）；需二次确认。
- 权限：`gateway:quota:query` / `grant` / `revoke`。

## 3. 在线充值（控制台）

开通条件：部署配了充值汇率 `NETONAPI_QUOTA_PER_PRICE_UNIT`（每 1 分到账多少 μUSD），且至少有一个可用支付渠道。
没开通时整块只显示「暂未开通在线充值，请联系客户经理为您充值」。

交互（主流做法：先金额、后支付方式，用对话框不离开页面）：
1. 页面上选金额：快捷金额 ¥10 / ¥50 / ¥100 / ¥500（超出单笔上下限的不显示）或「其他金额」。实时显示「支付 ¥X，预计到账 $Y」；
   低于 / 高于单笔上下限（系统设置 `gateway.recharge.min_price` / `max_price`，单位分）直接提示。
2. 点「充值」弹出对话框：支付金额、预计到账、**支付方式列表**（运营启用的渠道），「确认支付」。
3. 确认后建单（`POST /app/gateway/recharge {price, channelCode}`；只收 price，额度由服务端按汇率算），对话框切到付款步骤：
   跳转类在新窗口打开收银台（被拦时给手动链接）、二维码类直接显示码、SDK 类显示参数；每 2 秒查一次订单
   （`GET /app/gateway/recharge/get/{id}`），最多 10 分钟。
4. 付款成功显示「已入账 $Y」，点「完成」关闭；关闭 / 超时 / 订单关闭都有对应提示，已付但回调慢的稍后会出现在流水里。

到账：支付平台回调 → payment 置订单已支付并在同一事务里发 `PayOrderPaidEvent` → 网关按订单号入账（幂等，
并发 / 重投只入一次；入账失败整笔回滚）。

## 4. 沙箱支付（只用来验证支付模块）

- 开关：系统设置 `payment.mock.enabled`。打开后真实平台全部停用、只剩 `sandbox_*` 通道（互斥是刻意的：生产误开会立刻收不到钱而被发现）。
- 选沙箱通道下单，支付地址是后端的**模拟收银台** `/app/pay/mock/checkout`，只有两个按钮：
  「支付成功」走与真实渠道**同一个回调入口**（订单已支付、入账）；「支付失败」订单保持待支付（与真实渠道一致，超时由关单任务关闭）。
- `sandbox_alipay` 不是支付宝官方沙箱，只是方式标成支付宝的本地模拟通道；测的是我们自己的下单 / 回调 / 入账 / 失败路径。
- 收银台通道列表与下单用同一条互斥：开关关着时不列 `sandbox_*`，开着时不列真实通道（用户看到的每条通道都真能下单）。
- **正式环境状态（2026-10-29）**：已关闭（`payment.mock.enabled = false`），`sandbox_alipay` / `sandbox_wechat` 两条通道已停用；在配好真实渠道之前，用户端充值页只显示「联系管理员充值」，充值走管理员手动充值。
- **正式收款前必须关掉**，配真实渠道。上线前验证真实支付宝：用支付宝开放平台的官方沙箱应用，把真实支付宝渠道的
  `serverUrl` 指向沙箱网关，签名、回调、查单都走一遍，再切正式网关。
- 详见 module-payment 的 `docs/mock-payment.md`。

## 5. 掉单处理：同步支付状态

用户付了钱但回调没到（渠道抖动、回调地址配错）：
- 定时对账任务 `pay-order-reconcile` 每轮对超过 2 分钟的待支付订单向平台查单，平台确认已付且金额相符才置为已支付。
- 管理台「支付订单」对待支付订单提供「**同步支付状态**」（`POST /admin/pay/order/sync/{id}`，权限 `pay:order:sync`，默认授给财务）：
  立即对这一笔查单，结果是 已入账 / 平台显示未付 / 渠道不支持查单（沙箱、多数四方）/ 查单失败 / 金额不符（不入账，需人工核查）/ 已不是待支付。
- **没有「手动标记已支付」**：没有平台凭证就改订单状态等于凭空发钱。确认线下已收款的，用管理员手动充值。

## 6. 部署配置

| 配置 | 说明 |
|---|---|
| `NETONAPI_QUOTA_PER_PRICE_UNIT` | 汇率（每 1 分 → μUSD），没配 = 在线充值未开通。测试服现为 1389（¥7.2 = $1），正式汇率待定 |
| `NETONAPI_PAY_NOTIFY_BASE` / `NETONAPI_PAY_RETURN_URL` | 支付回调基址 / 付款后返回地址 |
| `payment.mock.enabled`（系统设置） | 沙箱开关，正式收款前关闭 |
